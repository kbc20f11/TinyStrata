# Measured speed — AMD Radeon RX 9060 XT (HIP)

The Qwen, Gemma and LFM rows were measured on **2026-10-28** using Windows 11, a Radeon RX 9060 XT (gfx1200, 16 GB; driver 32.0.32015.7029), a Ryzen 9 7945HX3D and 64 GB of system RAM, with the same three model files as in the main [README](../../README.md). INT8 KV and VMM growth with a 4 MiB allocation quantum were enabled. Context capacity, input chunks and Expert placement were automatic. Qwen and Gemma used MTP 3 and a GPU-resident image encoder; LFM used neither.

Protocol for the Qwen/Gemma/LFM rows: [tinystrata-bench-v1](../README.md#english), engine code [ef329af](https://github.com/kbc20f11/TinyStrata/commit/ef329af), seed 1234, four independent API starts per model.

## Clover causal and native block diffusion (2026-10-31)

Measured on **2026-10-31** on the same RX 9060 XT 16 GB (gfx1200), Ryzen 9 7945HX3D and 64 GB RAM PC, with Windows 11 build 26300 and AMD driver **32.0.32015.7029**. All five profiles use the same official Q4_0 model and native binary built from engine source [7f25f25](https://github.com/kbc20f11/TinyStrata/commit/7f25f25a878b309e35d899059e3c4f5a63b5c13d). The four INT8 profiles recorded API/source 7f25f25; the additional causal FP8 profile recorded [156a359](https://github.com/kbc20f11/TinyStrata/commit/156a3591fa6ed3a652854917b5a8f4145cd53b16), with the same benchmark runner, model and native binary. The Qwen/Gemma/LFM and RX 9070 XT measurements remain unchanged.

Each profile completed **four independent API starts**: **20 starts / 160 measured requests** in total. Each start ran a separate warm-up, the three canonical generation prompts twice at 128 output tokens, and exact 4K/16K inputs once each at 32 output tokens. Every profile returned **3,072 short-generation tokens + 128 after 4K + 128 after 16K = 3,328 final output tokens**. Native and API output counts agree. Input KV was not reused. Clover has no image encoder; image timing is **N/A**.

All profiles use **128K maximum context, KV growth and thinking enabled**, seed **1234**, greedy generation, `top_p=1`, `top_k=64`, `min_p=0`, `presence_penalty=0.9`, `frequency_penalty=0` and `repetition_penalty=1.05`. No tuning environment variable was set. The standard causal row uses the common `tinystrata-bench-v1` profile; the tuned causal INT8/FP8 and block rows are explicitly labelled variants. KV format is shown in the table. Block diffusion is native **LowConfidence generation**, not the optional draft/self-speculative route measured in the older D3/D4 tables.

The INT8 worker/chunk adjustment improves short causal generation by **8.3%** and generation after 16K by **9.3%** versus this new standard profile. It also changes workspace size and Expert cache capacity, so it is a **whole-profile comparison**. Both block profiles are slower than causal generation on this PC; causal decoding remains the default. The application’s automatic KV policy remains separate from the common INT8 benchmark profile. With the same W9/C1024 settings and measured cache capacity, causal FP8 reaches **49.04 tok/s** for short generation (**+0.2%** versus INT8) and **44.40 tok/s** after 16K (**+10.6%**); its 16K input rate is **714.52 tok/s** versus **719.56** for INT8. This is a throughput comparison, not a quality evaluation of FP8.

### Count and timing audit

Only final returned tokens, including thinking, contribute to tok/s. Repeated predictions of masked positions and causal replay are not extra output tokens; their execution time is included in native decode time. The following totals cover **24 short-generation requests / 3,072 returned tokens** per profile.

| Block profile | Resolved blocks | Denoising passes | Passes / block | Preview ms | Replay ms | Remaining decode ms | Selector ms, included in preview |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| B4, >0.95 | 768 | 2,416 | 3.146 | 69,139.0 | 19,346.9 | 221.2 | 42.4 |
| B32, >0.95 | 96 | 2,364 | 24.625 | 209,372.8 | 6,330.1 | 131.6 | 73.7 |

`Preview ms` includes full preview, confidence selection and freezing, including CPU Expert work and synchronization. **Selector time is a subset**, not an additional phase. Remaining time is `decode_ms - preview_ms - replay_ms`. On this Radeon, INT8 preview uses WMMA for blocks of at least 16 positions and SIMT for B1/B2/B4/B8. The recorded logical Attention-layer evaluations across all 32 measured requests were **B4: 0 WMMA / 26,080 SIMT; B32: 25,720 WMMA / 0 SIMT**; these are route counters, not individual GPU kernel-launch counts.

### Optimization controls and limits

A separate native control held Expert placement fixed at **6,040 slots / 10,687,610,880 bytes (9.954 GiB)**, with INT8, nine workers, chunk 1,024, 128K context, the three canonical prompts and 128 output tokens per request. GPU confidence selection reduced full-logit host copies; router parallelization and the GDN tile change were then tested. B4/B32 rates were **25.17 / 7.75 tok/s** for the CPU selector with old kernels, **27.78 / 9.94** for the GPU selector with old kernels, and **28.77 / 10.79** for the GPU selector with the adopted router/GDN changes. All **12 nontrivial comparisons** against the CPU-selector/old-kernel reference matched output token hashes, pass counts and cache allocation (two GPU implementations × two block sizes × three prompts). These screening values are distinct from the formal API table and must not be added as percentage gains.

Preview MMVQ, replay GEMM, preview-cache replacement variants and an initial all-misses streaming path were tested and not adopted: none gave a consistent benefit across the screened block widths; some also changed placement, token traces or denoising counts. WMMA preview passed **42 FP64-reference shapes** and **113 common INT8 Attention reference cases**. In two stress shapes, the older SIMT result exceeded its FP64 bound; the WMMA candidate passed the unchanged FP64 bounds. This numerical coverage does not establish identical generated answers.

A further **old/new causal ABBA control** used four total native starts (two per binary), three prompts per start, 128 output tokens each, INT8, W9/C1024, 128K, KV growth and the same fixed 6,040-slot placement. The old binary reached **40.27 tok/s** and the new binary **39.94 tok/s**, a **0.8% decrease**; token hashes agreed across all three prompts and all four starts. This control did **not** demonstrate a causal speedup. It is a separate fixed-placement native comparison, not another four-start-per-profile API result, and the difference is not assumed to be measurement noise.

### Answer quality and streaming behavior

In eight controlled reasoning tasks, causal INT8 generation completed **8/8 correctly**. B4 at threshold 0.95 completed **seven correctly**, with one still unfinished at the **4,096-token** cap; that unfinished case is not counted as a wrong completed answer. Separate B32 checks found an incorrect expected zero in a generated `sum_array([-1, 2, -3, -4])` unit test under both the previous SIMT path and WMMA. The separate causal sample generated three tests with correct expected sums, using different examples. A Japanese request for three items also produced three under the old path and two under WMMA. Block generation therefore does **not** guarantee causal output, the same distribution or equivalent answer quality.

Block output is streamed only after the whole current block has been resolved. Positive-temperature sampling uses the host confidence selector, so these greedy GPU-selector timings do not characterize sampled generation. Causal remains the default; block diffusion and the older self-speculative route are explicit options.

### Reproduce these profiles

Use the public runner with the matching model/binary installed. Keep each result in a new directory:

```powershell
python benchmark/run.py --model clover --clover-mode causal --runs 4 --output benchmark-output/clover-standard
python benchmark/run.py --model clover --clover-mode causal --kv-type int8 --cpu-workers 9 --chunk 1024 --runs 4 --output benchmark-output/clover-tuned
python benchmark/run.py --model clover --clover-mode causal --kv-type fp8-mma --cpu-workers 9 --chunk 1024 --runs 4 --output benchmark-output/clover-tuned-fp8
python benchmark/run.py --model clover --clover-mode diffusion --kv-type int8 --cpu-workers 9 --chunk 1024 --clover-block-size 4 --clover-threshold 0.95 --runs 4 --output benchmark-output/clover-block4
python benchmark/run.py --model clover --clover-mode diffusion --kv-type int8 --cpu-workers 9 --chunk 1024 --clover-block-size 32 --clover-threshold 0.95 --runs 4 --output benchmark-output/clover-block32
```

The block profiles use `tinystrata-bench-v1-clover-diffusion`; the manual causal profile uses `tinystrata-bench-v1-clover-causal-variant`. The canonical workload hashes remain unchanged. Raw logs and local scripts are not included in Git.

### Workload-dependent choice

- **Standard comparison:** `standard-int8-d0` retains the common v1 INT8/automatic profile. `stock-fp8-d0` is the matching FP8 option with automatic workers/chunk.
- **Causal tuning for this PC:** `tuned-fp8-d0-w9-c1024` reaches **52.12 tok/s** for short generation and **46.82 tok/s** after 16K, versus **47.58 / 41.90 tok/s** for the automatic FP8 baseline: **+9.5% / +11.7%**. Its 4K/16K input rates are **777.54 / 709.39 tok/s**, about **1.6% lower** than that baseline. It uses no tuning environment variable.
- **Short-input generation:** `tuned-int8-d4-w9-c1024` is fastest here at **59.06 tok/s**, **24.1% above the automatic FP8 baseline** (23.6% above standard INT8). However, after 16K it falls to **28.21 tok/s**, **32.7% below automatic FP8** and **26.5% below standard INT8**. It is a short-input option, not a general speed winner. Its `STRATA_TSUM=1` override and larger Expert cache are part of the measured configuration.
- D3 and the other D4 chunk sizes also improve short generation but remain slower for generation after 16K than the causal profiles. The shared self-speculation default therefore stays **D0**. The explicitly selected local tuning does not change the other model profiles or impose those worker/chunk choices on other PCs.
