# Inkling 2 Mini on RX 9060 XT 16 GB

Windows, Ryzen 9 7945HX3D, RX 9060 XT 16 GB (`gfx1200`), driver `32.0.32015.7029` and managed ROCm `10.2.0a20260930`. Both builds use the same Unsloth `UD-IQ4_XS` weights, 256K context limit, FP8 KV, 512-token input chunks, GPU Vision and no draft model. The staged API used the default placement and selected the discrete GPU.

## v2 Inkling extension

| Build | Starts | Generation tok/s | 4K input tok/s | 16K input tok/s | Image first output / complete (s) |
|---|---:|---:|---:|---:|---:|
| Fixed GPU KV with expanded dense weights | 4 | 19.70 | 335.69 | 332.12 | 2.80 / 9.31 |
| Growing GPU KV with compact dense weights | 1 | 37.39 | 392.66 | 384.12 | 2.20 / 5.30 |

The current result is a diagnostic single start with the v2 workload, including two repeats of each of the three text generation cases. Generation increased 89.8%. A separate 128-token greedy code case with the GPU image encoder resident measured 39.74 tok/s on the same final binary. Earlier independent starts measured 39.70 and 39.99 tok/s during tuning.

The growing route maps 4,096 global KV rows at startup, keeps the 262,144-token limit and holds the KV payload in VRAM. The benchmark started with 2,591 of 3,072 Experts in VRAM. As more KV is used, Experts return pages and keep their original weights available in RAM. The Q8_0 embedding and attention output tensors and the Q6_K output head keep their original storage. They preserve the existing BF16 rounding used for these weights in the kernels. Expert placement can affect the CPU and GPU rounding of individual runs.

## Workflow checks

In the same API process, the 16K input ran to completion and a 34,184-token shipping dossier returned all nine expected facts with no extra keys. A follow-up read the GPU-encoded label and reused 34,288 prompt tokens. Independent image input, replacement with a different image of the same size, and retry after invalid image input passed. A request beyond 256K returned HTTP 400, and a short retry succeeded.

The dossier committed 36,864 global KV rows, with zero host KV and 2,483 GPU Experts. A new short conversation returned to 4,096 rows and 2,591 GPU Experts. An explicit 32K FP16 configuration also completed a 4K input and its reply. The longest tested working input was 34K. The test confirmed that the API exposed the 256K limit and rejected oversized requests. It did not fill the entire 256K backing or reproduce a physical GPU allocation failure.

## Packed FP8 reads during decode

RDNA 4 uses packed FP8-to-FP32 expansion for single-token attention with FP8 KV. The existing KV format, per-token scales, and FP32 reductions are preserved. `STRATA_INK_HIP_PACKED_FP8_DECODE=0` selects scalar expansion. The device probe matched all 256 byte encodings in all four packed positions on the RX 9060 XT. The conversion was adapted from [Project Maya's packed FP8 work](https://github.com/mw00/project-maya/commit/c5f5a354).

The table gives median generation rates from three deterministic API requests per arm. Each set started with a fresh prompt and reused the prefix for the next two requests. The tests used the pinned UD-IQ4_XS weights, FP8 KV, GPU Vision resident, and drafting off.

| Placement and input | Scalar tok/s | Packed tok/s | Change |
|---|---:|---:|---:|
| Automatic, 1,466 tokens | 36.0 | 36.3 | +0.8% |
| Automatic, 16,552 tokens | 31.4 | 33.5 | +6.7% |
| 1,923 GPU Experts in both runs, 16,552 tokens, packed first | 24.9 | 26.8 | +7.6% |

Both paths returned the same answers and token counts, with all nine requested facts correct. The automatic-placement test also passed image replacement and retry after invalid image input. The reversed-order test used a 32K context limit to hold Expert placement fixed. gfx1100 and gfx1201 were checked by compilation and disassembly, with real inference measured on gfx1200.
